# Reviewed Architecture Proposals — 2026-07-26

This record preserves proposals removed from `ROADMAP.md` and the decision made for each. It is historical context, not an implementation backlog.

## Annex C — Roadmap revisions and architectural refinements

### APIC timer / per-CPU sequencing

**Original proposal:** Move APIC Timer / HPET adoption and per-CPU state ahead of Platform v1 and Network v1 because PIT timing may introduce jitter in heartbeats, timeouts, and retransmission.

**Decision: deferred.** Keep this in the Continuous Core lane. The Core change rule requires a measured outward-contract need before it becomes a milestone blocker. Destination: `ROADMAP.md` Continuous Core lane.

### Generation-tagged capability revocation

**Original proposal:** Use epoch/generation-tagged Ring 0 resource handles so service restart or supervisor revocation invalidates stale handles at the IPC barrier in constant time.

**Decision: already implemented.** `src/capabilities.rs` generation-tags grants and invalidates stale capabilities on revocation. Destination: Core v1 demonstrated evidence in `ROADMAP.md`.

### Zero-copy IPC buffer grants

**Original proposal:** Add Ring 0 shared-memory grant pages or ring buffers for bulk `Value::Stream`, `Value::Bytes`, and `Value::Table` payloads, keeping typed descriptors for the control plane.

**Decision: deferred.** Add only when measured bulk-transfer workloads justify the ownership and recovery complexity. Destination: this review record until then.

### Native LogOS WIT host

**Original proposal:** Scope Applications v1 around native LogOS WIT component-host mappings rather than generic WASI so WASM receives typed capability contracts directly.

**Decision: adopted.** LogOS WIT is the native host contract; WASI is compatibility only. Destination: Applications v1 in `ROADMAP.md`.

## Annex D — Repository and workspace architecture

### Cargo workspace and no-std isolation

**Original proposal:** Use a resolver-v2 root workspace with global dependency pins; keep `core/*` and `drivers/*` strictly `no_std`; have `services/*` and `flow/*` use `logos-abi` contracts.

**Decision: adopted with staged migration.** Create a workspace by extracting `logos-core`, then platform and driver crates, then `logos-terminal`, while retaining `logos-uefi` as the boot binary and passing QEMU after each extraction. Add `logos-abi` only when the first independently built native service needs it. Destination: Repository migration in `ROADMAP.md`.

### Flow compiler decoupling

**Original proposal:** Split Flow into `flow-parser`, `flow-types`, `flow-runtime`, and `flow-schema`, compiling on both target and host for `flow-ls` and `flow check --json`.

**Decision: deferred.** No Flow implementation exists yet; select its crate boundaries when Flow reaches implementation, rather than creating empty crates. Destination: this review record until Flow work begins.

## Annex E — External architecture review notes

### Inference and model ownership

**Original proposal:** Define an owner for `model:/local/default`, including model loading, inference scheduling, accelerator binding, and local-versus-remote routing; place it in System, Runtime, or both.

**Decision: adopted.** `system.inference` is the System owner; Runtime receives scoped invocation grants. Accelerator-driver work is deferred. Destination: Platform v1 in `ROADMAP.md`, the naming register, and `ARCHITECTURE.md`.

### Flow semantic dry-run

**Original proposal:** Add `flow simulate <script>` using command effect classification to preview service restarts, deletes, and capability use before execution.

**Decision: adopted.** Simulation is non-executing and best-effort; it reports predicted privileged effects, targets, and required capabilities. Destination: Flow Phase 13 in `FLOW.md`.

### Tiered and expiring consent

**Original proposal:** Add standing approval with scope, expiry, and revocation, distinct from single-use grants and durable capabilities; audit the approval itself.

**Decision: adopted.** Standing approvals are scoped, expiring, revocable policy grants with separate audit records. Destination: Platform v1 and the capability model in `ARCHITECTURE.md`.

### Taint tracking for untrusted external content

**Original proposal:** Mark values from external sources and block a scope holding both untrusted content and privileged capabilities without sanitization or re-authorization.

**Decision: deferred.** Require explicit re-approval when untrusted content would trigger a privileged agent effect. Defer global taint tracking until a narrower information-flow design is justified. Destination: AI-addressable operation in `ROADMAP.md` and `ARCHITECTURE.md`.

### Decision trace distinct from action audit

**Original proposal:** Store bounded structured decision traces for agent actions, correlated with audit entries and retained under separate sensitive-data policy.

**Decision: adopted with a privacy boundary.** Record policy outcome, user-intent reference, and structured tool inputs and outputs; exclude private model reasoning. Destination: AI-addressable operation in `ROADMAP.md` and `ARCHITECTURE.md`.

### Agent memory primitive

**Original proposal:** Decide whether agent memory is a Store namespace with retention, redaction, and workspace visibility policy or a distinct primitive.

**Decision: adopted as Store policy.** Agent memory uses a Store namespace; no new primitive is introduced. Destination: Persistence v1 and `ARCHITECTURE.md`.

### Sequencing note

**Original note:** These proposals should not block Console v1 or Platform v1; inference ownership and `flow simulate` should be designed with their respective Runtime and capability-preflight work.

**Decision: adopted.** All accepted items are attached to their existing milestones and none changes the Console v1 or Platform v1 ordering.

## Project review — 2026-07-25

### Original review

The review proposed a capability-backed dynamic allocator, service manifests and supervision, a hardware-abstraction layer, structured errors, async IPC with an executor, a grapheme-cluster terminal, a consolidated host-side test harness, custom Clippy rules, structured trace export, pre-commit hooks, CI, ADRs, dependency visualization, and broad property testing. It referenced `DESIGN.md` for a four-phase migration plan. The source review duplicated this summary verbatim.

### Decisions

- **Capability-backed allocator: deferred.** Core v1's fixed bounds are deliberate and marked with upgrade conditions; add an allocator only when a concrete milestone needs one.
- **Service manifests and supervision: retained.** This is already Platform v1 work, not a new Phase 1 prerequisite.
- **Hardware-abstraction layer: deferred.** Extract small hardware seams only when the staged crate split or a second architecture proves a need; do not add a general HAL now.
- **Structured errors: retained at public boundaries.** Apply them to session and service protocols rather than replacing every internal `Option`.
- **Async executor: deferred.** The existing scheduler and IPC are event-driven with cancellation and bounded backpressure; no immediate executor consumer exists.
- **Grapheme-cluster terminal: deferred beyond Console v1.** The current byte/cell terminal needs a real text model before full Unicode layout is worthwhile.
- **Host-side tests: retained after `logos-core` extraction.** The staged workspace migration is the first clean host-test boundary.
- **CI: already implemented.** `.github/workflows/verify.yml` exists; retain and improve it only when a concrete verification gap appears.
- **Pre-commit hooks, custom Clippy lints, and dependency graph gate: rejected for now.** They add maintenance without an observed failure mode.
- **ADRs: use the existing decision-note rule.** Add a template only when an irreversible decision needs one.
- **Structured trace encoding: deferred to Remote v1.** The bounded console export is sufficient at the current milestone.
- **Property tests: retained selectively.** Prioritize capability handles, IPC queues, mappings, and cancellation as already listed in the Continuous Core lane.

**Review outcome:** do not integrate the source review as a roadmap. Its applicable items are already represented by Platform supervision, staged crate extraction with host-side tests, and targeted property tests.
